# Rule registry

Every decision the pipeline makes is taken by one of these rules and can be traced to it in the
output (rule IDs are written next to derived values and in the audit files). Status: **ported**
(in this repository, tested), **planned** (exists in the Giye archive, being ported).

## Sampling frame (stage 1)

| ID | Rule | Status |
|---|---|---|
| F1 | Purpose: the programme's own public description states a purpose within the field. In the Korean media-art archive that is art–technology (or art–science) convergence, media art, new media, or digital art. The programme's document is the evidence, not the institution's reputation. | ported |
| F2 | Cohort: participants are fixed by an open call, jury, selection, award, or residency. A curated or rented exhibition does not qualify. | ported |
| F3 | Territory: the programme is held in the archive's configured territory (`archive.territory`). Production recorded the sentence as `f3_korea`; the loader accepts that key as an alias of `f3_territory`. | ported |
| F4 | Roster: the participant list is verifiable in a public record (official page, catalogue, or press release). Coverage is members recorded / max(declared roster size, members recorded), and unknown when no size is declared (see F4 on the site). | ported |
| F5 | Period: the programme has editions since 2010 and recurs at least twice. A single edition counts only when it represents the field that year. The 2010 bound is the production census rule and is stored in the frame's own sentence; the software does not hard-code a year. | ported |

The five criteria were fixed before any candidate programme was examined (adopted 2026-09-20), so inclusion is not a judgement made after seeing who was selected. `giye.collect.frames` checks that each `frames.yml` entry records a decision (`included`, `excluded`, `adjacent`, and the production verdicts `planned` and `no_public_roster`) and a sentence for F1–F5. It does not re-decide them.

Collection policy (not an F-rule): robots.txt is checked before every request and before every redirect hop (RFC 9309). The matcher is the longest matching Allow or Disallow (§2.2.2), on the product token in the User-Agent (§2.2.1). HTTP 2xx is parsed. HTTP 4xx is `unavailable_allowed` (the URL may be fetched). HTTP 5xx, a timeout, or a network error is `unreachable_disallowed` for this process only; the next process fetches robots.txt again. A parsed disallow raises `RobotsDisallowed`. An unreachable file raises `RobotsRefused`. The hop is not sent. `/robots.txt` is always allowed. When the live page is gone (HTTP 404 or 410, or the connection fails), an existing Internet Archive capture may be kept. Giye never asks the Archive to make a new capture. If robots.txt disallows the URL, the existing capture's URL and timestamp are recorded (`archive_link_only`, `direct_failure=robots`) and the bytes are not downloaded or kept. That is the only behaviour for a disallowed host. A robots.txt that answers HTTP 5xx or times out is recorded as `robots_unreachable`: a refusal for now, not sent to the Archive, and tried again on every later run. A host that cannot be reached at all (DNS failure, connection refused) counts as a failed connection: its existing Internet Archive capture is kept (`direct_failure=host unreachable`), or the URL is `unavailable` when there is none. Status lines written earlier as `robots_disallowed` with reason `robots_unreachable` are retried too. `giye evidence` writes its status file every 25 URLs, and a later run does not relabel its own captures. Platforms whose terms forbid collection (Instagram, Facebook, LinkedIn, X, Threads, TikTok, with their short-link and alternate hosts: threads.com, instagr.am, fb.com, fb.me, fb.watch, t.co, lnkd.in) are not requested. A config with `[collect.offline_roots]` is offline: `giye evidence` sends nothing to the Internet Archive, a URL that would have gone there is `unavailable` with `wayback=offline`, and a cited URL outside the offline roots is not fetched at all (`unavailable`, reason `outside offline roots`), so a missing network is not recorded as a robots refusal. The switch is derived from the offline roots, not a second setting, so an offline config cannot leave it on.

## Extraction (stage 2)

These decisions come from `extract_cvs_llm.py` and `apply_cv_extractions.py`. Production did not give them E/F/P/V ids. `giye.extract` keeps the same outcomes. A team is still refused at registration by T1 (`team_like`): a member's personal CV is not filed on the team unless `[extract] allow_team` is set.

| Decision | Rule |
|---|---|
| Schema | One response is a list of activities (`title`, `venue`, `year`, `activity_type`, `role`, `cv_section`, `upcoming`, `source_id`). An extra field, a type outside the production enums, or a year that is not an integer rejects the whole response. Two exceptions, because the reference archive's stored readings use them: an optional `note` (appended to `reviewer_note` on apply) and a missing `role` (read as ""). The schema sent to a model is unchanged: eight required fields and no `note`. |
| Unknown source | A row whose `source_id` is not one of the CV documents just read is dropped. The year and venue are checked against the text when grounding is on (next row; on by default). |
| Grounding | With `[extract] grounding` (default `true`), a CV row whose year does not occur in the text of the CV it cites (as a number of its own), or whose non-empty venue does not occur there by rule G-V, gets `ungrounded=year`, `ungrounded=venue`, `ungrounded=year+venue` or (G-T, below) `ungrounded=title` in its note and `publishable=no`. G-V, first match wins, every occurrence on word boundaries (`giye.normalize.match`: a Latin name may not start or end inside a word; a Hangul name may not start inside one, and may continue inside its word only with one particle or suffix from a closed list (`giye.normalize.match.HANGUL_TRAILERS`: case particles such as 에서, 의, 을, the copula, and the exhibition suffix 전/展), after which the word must end, because Korean puts the modifier of a compound first and the particle last. Before 2026-10-06 any continuation was allowed, so the truncated venue `부산현대미술` was grounded by `부산현대미술관` and E3 found 〈푸른 신호〉 in `푸른 신호등`; on the production copy of 2026-10-06 the closed list newly fails 8 of 57,529 publishable CV venues (each a name read out of a longer word, such as a city name read out of a festival name); before 2026-10-06 these were substring tests, software review round 6): (1) the whole venue occurs, both sides NFC, case-folded and whitespace-collapsed, failing that with punctuation and brackets replaced by a space; (2) its institution part occurs: the venue is split as V2 splits it (commas, slashes, round brackets, " - "), the parts are classified with the gazetteer as V3 classifies them, and the first part that is not a place is the institution (the first part when all are places); it is matched in the normalised form, then with spaces removed on both sides. City and country parts need not occur, and part order does not matter; (3) cross-script: a Latin institution part matches when some run of one to six Hangul words in the text has the same V9 reading (glossary and romanisation), and a Hangul part when one of its V9 readings equals the bag of some run of one to eight Latin words; (4) bracketed other-script name: when the institution part and the one fragment of a round bracket next to it form a V2 bracket pair ("한글명 (English Name), City" or the reverse), one side is mostly Hangul and the other Latin, and the bracketed partner is not a V3 place, the partner is tested by (2) and (3) as well, and either name grounds the venue. An institution part of generic venue words only (`Museum of Art`, `Art`, `Residency`; the V7e/V9 test that a name holds a proper word) grounds nothing by (2)–(4); such a venue holds only when the whole venue occurs where a venue starts in the text (after a line start, punctuation or a number), so `Residency, Seoul` is not grounded by `Example Residency, Seoul` and `Museum of Art, Busan` is not grounded by `Seoul Museum of Art`. G-T: a row with an empty venue claims nothing by its venue, so its title is read instead: some part of the title (split at ` / `, ` | `, ` - ` and brackets, two characters or more) must occur in the text with punctuation and spaces removed on both sides, or the row gets `ungrounded=title` (with `year+` when the year fails too). Why only empty-venue rows: on the production copy of 2026-10-06 (57,529 publishable CV rows with a text on disk) the part test fails 636 rows, and the sampled failures are correct entries a model recomposed (a programme and its host joined, a translation added); of the 4,472 empty-venue rows it fails 51 (1.1%). Not checked, by design: the title of a row with a venue (above), so an invented title at a venue and year that occur is published, the city or country next to an institution that occurs, and a same-script bracket next to it (`Example Culture Center (Imaginary Hall)`), which rule (4) does not read as a second form of the name. A row is never deleted, it does not hide a self-reported copy of the event, and `giye extract` prints the count by reason. A CV without a text file on disk is not checked (`unchecked_no_text`). Roster rows are not model output and are not checked. Why: the schema check validates the shape of a reading, not its content, so a schema-valid invented venue would be published with the CV as its source (software review, round 5). Why the institution part: with the whole-venue test (2026-10-06, production copy) 2,758 of 58,373 publishable CV rows (4.7%) were marked, and most venue failures were correct readings: "Venue, City, Country" where the CV writes "Venue (City, Country)" or puts the city on another line, a name the CV writes without spaces, or a name the reading gives in the other script. The city is not the claim a reader checks; the institution is. Why on: with G-V the same copy (ledger of 2026-10-06) marks 654 of 58,373 (1.1%): 83 year only, 570 venue only, 1 both; of the 570, 390 have an institution part in a script other than the text's that rule 3 cannot read and 180 have no match. Why rule 4 (author's delegate, 2026-10-06): a reading that gives one institution in two scripts, one in brackets, wrote both forms of one name, and one form found in the source grounds it. A bracketed place ("Hall (Seoul)"), a same-script bracket (an acronym, a branch, "Client: …") and a non-Latin second script (Hanja) are not a second form of the name and are not used. The counts above predate rule 4 and the word-boundary and generic-word changes of 2026-10-06; `giye extract` prints the current count by reason, and a paper should cite that count, not these. |
| Private rows | `publishable=no` for sections education, employment, teaching, press, scholarship, and service, and for a title or role that matches the production scholarship / peer-review pattern. The row stays in the ledger. |
| Upcoming | A future year marked upcoming is `publishable=no`. This year's upcoming row stays visible and the role gains `(예정)`. A past year marked upcoming is shown without that suffix: the label has gone stale. |
| Korean / English repeat | Inside the rows one extraction is adding, two lines with the same year, the same normalised venue, and titles that match or contain each other (Hangul floor 4 characters, Latin floor 6) collapse to the first row. |
| X2 Cross-language fold | After every file is applied, two publishable `cv:` rows of one person from two different CV documents fold when one is Korean (Hangul in the title or the venue) and the other Latin script, with the same year and activity type, each venue names exactly one institution (V2/V3), and the two read as one institution: the same V4/V7a–d key (a qualifier such as 외 is stripped), the same V7e word bag, or a V9 Hangul reading equal to the Latin bag (V8b offices never). A name of generic venue words only (the V4 generic test: `Art Space`, `갤러리`) never folds, and two venues that name different cities (or, without a city, different countries) never fold: `Art Space, 대구` and `Art Space, Berlin` are two events (pre-release audit N-2, 2026-10-06). The match must be one to one inside that person, year, and type, counting rows from every document; an empty venue, or one that is only a place, never folds. When the two titles are in the same script (both Latin: the Latin row has no Hangul by definition, so this is a Korean CV row that carries an English title), their word bags must also overlap: Jaccard ≥ 0.5 over case-folded letter runs of two or more characters, with numbers and years dropped. A Hangul and a Latin title cannot be compared without a translation, so a cross-script pair keeps the venue rule alone. The row in the archive's first configured language (`[archive] languages`) stays; the other gets `publishable=no` and `superseded_by=<kept activity_id>; rule=X2`. Marks are cleared at the start of every apply and decided again, so the fold is idempotent and reversible; `work/cv_folds.csv` lists every fold. Why: a person with a Korean and an English CV (or two records joined by a merge) listed one exhibition twice, and the in-file repeat rule compares titles, which a translation does not share. The venue is the evidence; one-to-one keeps two shows at one museum in one year apart, and two documents keep a single bilingual CV's separate entries apart (on the production ledger, 6 of 9 same-document pairs were different shows). The title guard exists because a venue match alone folded two unrelated Latin titles at one museum in one year (software review, round 5); the one production fold with two Latin titles differs only by an edition mark and has Jaccard 1.0 once the number is dropped; half the bag means one shared generic word such as "exhibition" is not enough on its own. The threshold has not been audited on a sample of pairs, and two titles that share two generic words still fold ("Night Garden Exhibition" / "Night Machines Exhibition", Jaccard 0.5; software review, round 6). The id is X2 because C1 is the planned cluster rule (stage 6). |
| Public record wins | If another origin already records the same title and year and that row is not self-reported, the CV copy is skipped. A self-reported row (`SELF_SUBMITTED`, or a note starting `from_arko_career_text`) is set `publishable=no` and noted `superseded_by_cv`. |
| Owner | A `cv:<source_id>` row belongs to the `ledger_id` on that CV source, not to the id written on the extraction file. |
| Superseded file | An extraction file whose id is not an artist is skipped when a live artist's file already covers the same sources. |
| Content id | The activity id is the ledger uuid5 (`giye.ledger.ids`). The same CV line keeps its id across applies. A repeated key in one write gets an ordinal. A dropped line is not given a new id. |
| Re-read | The CV is extracted again when a source content hash, the prompt SHA-256, or the model no longer matches the extraction file. The replay cache is keyed by the source ids and the content hash of each CV text (source id order), the prompt hash, and the model. Why the source ids: two people can hold the same CV text under two source ids (a duo's shared page), and each response names the source id of every row; keyed by the text alone, the second response overwrote the first. A cache written under the older text-only key is still read, unless all of its rows name other sources. |
| No silent wipe | A reading that would remove every CV row a person has is a replay miss, not an empty extraction: the response had rows but none named a source sent with it, or it has no rows while the ledger holds `cv:` rows from those sources. No extraction file is written, so the ledger keeps its rows and a later run reads the CV again. |
| Replay only | `giye extract --replay-only` reaches no network. Only sources served from a configured `[collect.offline_roots]` directory (the demo fixtures) are pulled; every other source keeps its snapshot, its fetch columns are not written, and no `cv_pull_failed` item is queued. |

## Identity (stage 4)

Two steps, and they are not the same decision.

**Attachment** joins a new roster row to a person who is already in the ledger. It runs when the row is collected. One of A1–A6 has to fire. The rule id is written on that membership row (`attach_rule`). An attached row's printed name is never dropped: a spelling the person does not already carry (`name_ko`, `name_en` or an alias, compared with whitespace collapsed and case folded) is added to `aliases`, and runs of whitespace in a roster name are one space. A row that no rule attaches becomes a new person, and the membership says `first`. A same-name candidate that no rule takes is queued (`possible_same_person`). It is not attached. Two lines of one roster edition are two people: a line is never attached to a person an earlier line of the same edition was put on, even when every name is identical. A same-name pair of lines becomes two records and is queued with detail ending `(same edition)`; a re-collection puts each line back on its own record (A1, in line order). A collector identity key (A5) still reads every record. Why: two lines on one roster page are the strongest evidence of two people the data hold, and before 2026-10-06 a shared name or a shared romanisation made the second line an alias of the first, so a listed person had no record. A team member found by team expansion follows the same rules: a member A1–A4 do not attach (a Latin-only personal name, or a common Korean name on another programme) gets a new record with the team's membership, and the pair is queued with detail ending `(team member, name only)`. The member is never dropped. A membership that team expansion writes records `attach_rule` `team:<team ledger id>` (the team whose credit put the member on that edition), so every membership row names the rule that wrote it. A membership the member already had on that edition is not rewritten.

Name keys (`giye.resolve.attach.name_keys`, read by A1–A4): a Hangul run of at least two syllables, a sorted pair of Latin tokens (a token is a run of Latin-script letters of at least two letters, accents included), the compact spelling (letters and digits, lower case) of a part with fewer than two Hangul syllables and fewer than two Latin tokens when it is at least three characters, else the compact spelling of the whole name. A mixed-script name with one Hangul syllable (a Latin word plus one syllable) takes the third key, so it matches its own earlier record whether or not that record also has a two-token English name. Latin text in every key is folded: case folded, diacritics removed (NFKD), and the letters with no decomposition mapped to their plain form (ø→o, ł→l, đ→d, ð→d, þ→th, æ→ae, œ→oe, ß→ss). Why fold: an English-language roster often prints a name without its accents, and `José García` and `Jose Garcia` are one spelling of one name. Folding removes marks and never drops a letter, so `García` (`garcia`) and `Garcés` (`garces`) stay different keys. Before 2026-10-06 a token was `[A-Za-z]+`, which cut `José García` to `jos garc` and gave it the key of `José Garcés`.

Differing Hangul names (A1–A4 and the A6 name test): when both the roster row and a stored row carry a Hangul name of two syllables or more (`name_ko`, `name_en` or an alias, spaces removed) and they share none, the rows do not have the same name, whatever Latin key they share. The pair is queued (`possible_same_person`, detail ending `(hangul names differ)`). Why: different Hangul names can romanise identically (`윤서정` and `윤서중` are both `Seojung Yoon`), and before 2026-10-06 A1 and A2 joined them on the shared English name. A stored alias counts as a spelling of the row, so a person already carrying `김하눌` as an alias still meets a roster that prints `김하눌`.

**Merging** joins two records that already exist. It runs in `giye resolve`, and only on written evidence (E1–E4, with X1 when the scripts differ). A team is not merged with a person (T1). An exact Korean and English name pair, across programmes, is not by itself a join. A Latin-only personal name is not joined to another record on the name alone, whether that record is Latin-only or a Hangul record whose English name agrees (author decision 2026-10-05 for two Latin-only names; extended to one Latin-only side 2026-10-06). A1 (same programme series) and A6 (same own website, with names that meet) still join them; elsewhere the pair goes to review. Once both records exist, E1–E4 may still merge them.

**Manual merges** (`giye merge`, `giye queue decide --decision merge`) keep the same documentary guarantee. The evidence string names a rule and a source: an E-code (`E1`–`E4`, or `X1+E1` … `X1+E4`) followed by a citation (an http(s) URL, a `source_id` registered in `cv_sources`, or a roster edition code: a `frame_code` on the ledger or `<frame_code>-<YYYY>`), or `H` (a person's judgement) followed by the reason and an ISO date. Anything else is refused. A date in `H` written another way (`01/01/2099`, `2026.01.15`) is refused, because only ISO dates are checked for being real and not in the future. An `H` merge of two records that the sources list as two people (separate lines of one roster edition, or two members of one team by `team=` or `팀 구성원:`) is allowed but prints a warning, and the stored evidence ends with `listed separately on <frame_code>` or `both members of team <name>`. The cited evidence is then checked against the ledger with the resolver's own code (`giye.resolve.decide.verify_merge_evidence`); a citation the data do not bear out is refused:

- `E1`: a cited URL's site (the E1 `url_key`) is a website of these two records and of no other living record, and the two records' names overlap as the resolver's E1 requires (Hangul with spaces removed, otherwise the lower-cased string; aliases included).
- `E2`: a cited CV source (a `cv_sources` id or its URL) belongs to one of the two records, and that CV's lines list a roster edition of the other that the CV's owner is not on (the E2 event pattern and year window).
- `E3`: the cited work title is a bracketed work both rosters credit, or one roster credits and the other's CV lists, within the year window.
- `E4`: the cited team name is a team both rosters credit with the team prefix.
- `E2`–`E4` also need a candidate pair, because the resolver tries these rules only on one: the same primary name (NFC, spaces removed, case folded), or names that meet (the same Hangul syllables, a shared attachment name key, or a shared romanisation key; `giye.resolve.attach.names_meet`).
- `X1+E1` … `X1+E4`: the two records' name keys (`LanguageModule.name_keys` of `name_ko` and `name_en`) intersect, and the E part holds as above. The X1 keys are the name condition.

Why the name and candidate conditions (software review, round 6): the cited fact alone does not tie two people. Two members of one team share the team credit (E4), two residents of one edition both appear in one CV's listing of it (E2), and a duo website lists both members (E1). The resolver never tries those pairs, so a manual merge of them needs `H`.
- `H`: every ISO date in the string is a real calendar date no later than today, and the reason has at least three words besides the date.

The code is stored as the merge's `rule=`. The public `Ledger.merge` is not a second path: it delegates to `merge_people`, so it runs the same evidence check, the T1 team/person refusal and the decided-distinct refusal, and refuses free text, an unknown rule id, or a `rule` that is not the code the evidence names; the automatic resolver writes through an internal path, because its merges are the rules firing. A pair a person decided `distinct` is refused unless the library call passes `override_distinct=True`, and an `H` that overrides it must carry a date on or after that decision's `decided_at` (a judgement made before the decision cannot be the reason to reverse it; software review, round 6); the evidence then ends "overrides distinct decision of <date>", and that queue item is rewritten to `decided=same` so it no longer reads `decided=different`. A distinct or merge decision records `decided_at=<date>` on the queue row; an older row without one is reported as `undated`. Why: a merge that cannot be traced to a document or to a dated, attributable judgement cannot be contested, and a stored `E1` that nobody checked would tell a reader that a shared website exists when it does not.

**Splits** (`giye split`, `giye.resolve.split.split_membership`) undo a wrong attachment. When a person judges that a roster membership one of A1–A6 joined to a record names a different person, `giye split --membership <ledger_id>@<frame_code> --evidence "H <reason>; YYYY-MM-DD"` gives that line a new record:

- The new record gets a fresh permanent `gy_id`, one past the highest ever issued (retired ids included), so no number is reused. Its name is the roster line's printed name: the line of that edition code in the collection reports (`work/rosters/*.csv`), from the membership's source page when one matches, whose printed names are spellings the old record carries (`name_ko`, `name_en` or an alias; attachment keeps them) and not spellings of another record on that edition. When exactly one line qualifies its names are used; otherwise the new record takes the old record's name. `--name-ko` / `--name-en` state the name instead (either one given replaces both). Names are stored as a roster insert stores them (a Latin-only name is copied into `name_ko`). The record is `STAGED`, cites the membership's `source_url` and `collected_at`, and is published like any other person.
- The membership and the activity rows whose `origin` is that edition code move to the new record, with their ids. The membership's `attach_rule` becomes `split:<rule>` (for example `split:A1`), so an audit of A-rule attachments (`python -m giye.audit sample attach`) no longer counts it as an attachment to an existing record. CV rows (`origin` `cv:<source_id>`) never move: a CV row belongs to the owner of its CV source.
- Both records' notes gain `split <ledger_id>@<frame_code> to <new ledger id>; split_evidence=H …; rule=H` (a `;` inside the evidence is stored as `,`, so the date stays in its segment). When the old record cited the split edition's page as its own `source_url` and no remaining membership cites that page, its `source_url` and `collected_at` move to the remaining membership with the earliest `collected_at` (then `frame_code`).
- A `possible_same_person` queue item on the pair is closed `decided=different` with `decided_at=` and `evidence_at_decision=`, so `giye resolve` treats the pair as decided distinct: it neither merges nor queues it again, a later E-rule only reopens that item, and `giye merge` refuses the pair without `override_distinct`.
- A later collection of that edition puts the line on the new record: a line that attachment would put on the old record for that edition code goes to the record it was split to (`giye.ledger.ledger._follow_split`), and the rule is `split:<rule>`. Why: re-collection repeats the same A-rule, which would otherwise join the line to the old record again. Two lines of one edition are two people, so the line that attaches to the old record is the split line.
- The old record keeps its `gy_id` and its page; nothing is retired or redirected.
- Refused: a record hidden by request (a split would publish part of its data), the record's only membership (nothing would remain), and evidence that is not a valid `H` (a reason of at least three words and an ISO date that is a real date no later than today, the check a manual `H` merge runs). Why only `H`: E1–E4 are evidence that two records are one person; no rule yet shows that a line names someone else, so a split is a dated judgement.
- `--dry-run` checks and prints the split without writing. `giye split --from <csv>` reads columns `membership_id`, `evidence` and optional `name_ko`, `name_en`; every row is checked before anything is written, and each table is written once, so one dated backup (`<file>-<date>-before-split.csv.gz`) covers the batch and a refused row (named by its row number) writes nothing.

Not moved by a split (open questions for the author): the old record's aliases taken from the split line's printed name, a website the line stated (`links` with that edition as `origin`), an `identity=` pin from the line, collaborations of that edition, and activities from that line's `extra_activities` whose `origin` is another code.

A later merge closes an attachment queue item when the item's detail names the dropped ledger id. The item was the near-miss; the merge is the evidence decision. Whether that close should stay is an open question (the ledger already did this for any `possible_same_person` item).

The family is the field file: a year suffix is stripped, then a declared prefix or an exact code. A Korean personal name shared with someone in a different programme is not the same person. | ported |

The first same-key row is reused. A name that is neither a personal name nor a group (Chinese characters, Hangul outside the surname shape below, a Latin string of seven or more tokens) takes A3 only when a same-key row is a recorded group; otherwise the pair is queued. Personal names (the language module's `personal_name`), Korean–English module: a Hangul name starting with a listed surname, two to four syllables without spaces or two to five with spaces (`김 하늘`), where the surname is a single listed surname or a compound one (남궁, 황보, 제갈, 사공, 선우, 서문, 독고, 동방); a spaced Hangul name of two to five syllables with a one-syllable word is also personal (`알렉스 리`, `마리아 김`: a foreign name written given name first). A Latin-only personal name is two to six tokens of Latin-script letters, accents included (`José García`, `Đặng Thị Lan`; a single letter counts), and every letter of the row is Latin; the rest of the string is only spaces, hyphens, apostrophes, or periods. One token is too common. Why positive evidence only: before 2026-10-06 every name outside the personal shape took A3, so spaced Hangul names, unlisted compound surnames, and Hangul spellings of foreign names were joined across programmes on the name alone. Why not every short Hangul string is personal: the team test reads a non-personal name's aliases and English name for group evidence, and a short group name without a team word would lose it. | ported |
| A4 | A same-key row exists and it has no roster membership yet. The first roster attaches to it. Only a bare Korean personal name reaches this branch. | ported |
| A5 | The collector's identity key matches a key already stored on a row. Checked before the name rules. A miss does not fall through, so two people the roster pinned apart stay apart. | ported |
| A6 | The same own website (not a social link) is owned by exactly one existing row, when the name rules and the identity key did not choose. It can join a different spelling. A link owned by two rows is not used. The names must also meet (the same Hangul syllables, a shared attachment name key, aliases included, or a shared romanisation key, X1) unless one side is a group (A3's positive test) and neither side is a personal name. So `윤가온` may join `Gaon Yoon`, but `Ann Lee` does not join `Bo Kim`, `김 하늘` does not join `박 서연`, and `山田太郎` does not join `Haneul Kim`. | E1 | Two records are the same person when they share a personal website. The key is the host, or host plus path on a shared platform (a blog host, a portfolio host, a video host). `www` and a trailing slash do not make a second site. Social links are not a personal site. The rows also need an overlapping name (Hangul with spaces removed, otherwise the lower-cased string). | ported |
| E2 | … when one's CV lists the other's roster appearance: the CV text matches that frame's event pattern and the CV year is within one year of the edition. | E3 | … when a bracketed work title (`〈…〉`, `<…>`, `《…》`, and the same family) on one roster row also appears on the other's roster row or CV, in the same year ±1. On the CV side the title must occur as whole words (the boundaries of G-V; spaces inside the title may differ), not as part of a word: 〈Sea〉 is not in "Research", 〈Light〉 not in "Lighthouse" (software review, round 6). | E4 | … when both roster rows credit the same team in the role, written with the field file's team prefix (`팀:` in the Korean media-art field). The normalised team name is at least 2 characters. This joins two rows of one candidate pair; it does not collapse every member of a team into one person. | ported |
| T1 | A record whose name looks like a team or collective is never merged with a person. A team row has `members=` or `rep=` in the note, two or more aliases the language module calls personal names, or a team word from the field file in the name. Exactly one side being a team blocks the merge. Two team rows may still merge with each other on E1. X1 drops a pair when either side is a team. A record that the ledger names as a member of the other also blocks the merge, whatever the team's name looks like: its `team=` value, or its `팀 구성원: <name> (<ledger id>)` note, names the other record (primary name, case, spaces and punctuation ignored, or ledger id), or the other record's `members=` lists it. Why: a Latin team name can have the shape of a personal name, so the team test reads it as a person, and E1 (shared website, a member's name among the team's aliases) joined a team to its own member. | ported |
| T2 | A team's members get the team's credit even when the record lists them only as aliases. A record that is positively a group (the T1 team test: a team word of the field file, a `members=` or `rep=` note, or a non-personal name with person-shaped aliases), whose own names (`name_ko`, `name_en`) are not personal names, and whose aliases hold two or more distinct personal names (the language module's `personal_name`) reads those aliases as its members, when it has no `members=` list and no `; group;` raw credit. An alias equal to one of the record's own names, or one with a team word (the team's English name), is not a member. Aliases that share a name key (`name_keys`: `김하늘`, `김 하늘`, `Haneul Kim`) are one person, written as one member with the first Hangul and the first Latin spelling; one person is not a team. The members then go through `expand_teams` like a `members=` list: each joins an existing person under A1–A4 or gets a new record (a `possible_same_person` item when the name keys hit a record no rule takes), is put on each of the team's editions (`attach_rule=team:<team ledger id>`), and receives the team's activities with the role `팀: <team>`. The team row stays (T1). A second run adds nothing. Why: the author's credit rule (2026-10-06), "participation as a team is decomposed and returned to the individuals, so they share the credit". Collectors often stored a team's members only as its aliases, so those people never received the team's programmes. Why the guards: a person's record keeps other spellings of their own name as aliases, and those must not become new people. | ported |
| X1 | Hangul and Latin spellings are candidate matches when their romanized keys intersect (`giye.resolve.names`). A candidate is merged only with E1–E4 evidence, recorded as `X1+E1` … `X1+E4`. No evidence queues the pair (`possible_same_person`). A shared frame code, a collector identity pin, or a team row drops the pair. A Korean row that already has a Latin name is paired whether or not that name meets the other row's keys; when it meets, the queue detail ends `(rule=x1_own_en)`. Why: until 2026-10-06 such a pair was skipped on the assumption that A2 had joined it, but A2 needs identical Latin tokens (`Do-yun Lee` is not `Doyun Lee`) and does not join a Latin-only personal name across programmes, so the likeliest duplicates were neither attached nor queued (software review, round 6). The open-pair count is a bound on the uncertainty only with these pairs in it. A pair a person already decided (distinct or dismiss, on the queue row) is not queued again. The pair is the unordered ids after following merges: a decision on A–B covers a later row that absorbed A or B (`merged <ledger id>` on the kept row; the item's own ledger id is already rewritten along a chain). An E-rule that did not fire at decision time reopens that same item and does not merge over the decision. | ported |

A same-script exact name (Unicode NFC, spaces removed, case folded) that no rule accepts is queued the same way, reason `possible_same_person`, detail `rule=same_script_exact`. It is not merged. A Latin-only personal name that A2 and A3 refuse is queued at attachment, same reason, detail ending `(latin name only)`. A pair already named by a queue item is not queued again, whatever the item's status. A dropped id in that item is read as the row that absorbed it. A done item whose pair was never actually joined is reopened (`reopened=wrong_close`) unless a person recorded `decided=same`, `decided=different`, or dismiss (`decided=dismissed`, status `dismissed`). A distinct or dismissed decision stays on that pair. The decision records `evidence_at_decision=` as the E-rule that held then, or `none`. A later run that sees a different E-rule reopens the same item (`reopened=new_evidence`) and names that rule. The pair is not merged, and a second item is not opened.

Every merge stores `merge_evidence=` (the rule and the concrete website key, CV line, work title, or team) and `rule=` on the kept row, and retires the dropped `gy_id` through `Ledger.merge` (`giye.ledger.Ledger.merge`). When the dropped row had itself absorbed others, its `merged <id>; merge_evidence=…; rule=…` groups move to the kept row before the new merge's markers, in order and without a marker the kept row already has, so a chain of merges still names the evidence and rule of every merge it holds.

The synthetic demo fires E1–E4, X1+E2, and T1 once each, records A1 on a membership row, shows A2 declining a Latin-only pair (queued as `latin name only`), and records `team:<team ledger id>` on the four expanded team-member memberships. See `examples/demo/EXPECTED.md`.

Attachment A1 and derived-value A1 (`active_since`, below) are different rules that share a letter. They are not renamed here.

## Ledger invariants (stage 3)

These are not sampling or identity rules. They are how the ledger keeps a fact attached to a source and to a permanent id. `giye.ledger` implements them.

| Invariant | Why |
|---|---|
| A `gy_id` is never reused and never renumbered from the row's position. The next id is one past the highest ever issued, retired ids included. | A published URL must keep working. Filling a gap, or numbering by the current sort order, would give someone else's page to a new row. |
| A merge retires the dropped `gy_id` into `gy_retired.csv` (`gy_id` → `merged_into_ledger_id`) and rewrites older retirements to the final survivor. | A chain of merges still redirects in one step. `Ledger.redirects()` maps each retired id to the survivor's current `gy_id`. |
| A merge requires an evidence string and a rule id (E1–E4 or whichever rule decided; `H` for a dated human judgement, see manual merges). | A retired id without a reason cannot be audited. The note on the kept row stores `merge_evidence=` and `rule=`. |
| An activity id is uuid5 of a fixed key (person, source, normalised title, year, type, venue, and the frame code for a collector row). The same key in one write gets an ordinal. | The same fact must keep its id across runs. Case and punctuation in a title are not a different fact; a different venue spelling is, because a tour has one row per stop. |
| A CV-derived row (`origin` `cv:<source_id>`) belongs to the owner of that CV source. The same-person rules read CV lines the same way: a line belongs to the owner of its `source_id` in `cv_sources`, followed through `merged <ledger id>` markers to the living record; a line with no registered source belongs to the file's `ledger_id` (or file name), followed the same way. A merge does not rename extraction files. | The extraction file keeps the ledger id it was made for. A merge updates `cv_sources.ledger_id` and can leave the activity on the retired id. The source's owner is the person the row belongs to. Until 2026-10-06 the resolver indexed CV lines by file name: after a merge the absorbed record's CV was ignored when the survivor had a file of its own, and the renamed file gave one person's CV to the other after a restore (software review, round 6). |
| Every ledger write of an existing file is copied to `data/work/backups/<file>-<YYYYMMDD>-before-<task>.csv` first. | A script must be able to put the previous bytes back. The task name says which write replaced them. |
| The backup is taken once per file and task in a run (one `giye` command, one process): the first write copies the file, later writes of the same file and task in that run reuse that copy. A later run gets its own copy (`-2`, `-3`, … on the same day); an existing copy is never overwritten. Copies are gzip-compressed (`.csv.gz`); every reader of backups accepts `.csv` and `.csv.gz`. | A full collect rewrites the same tables hundreds of times. A copy per write of the production register was about 2 GB per run, which would fill the disk within weeks. The bytes a run started from are what a restore needs; the run's intermediate states are reproducible by running it again. |
| Each table is written atomically (a temporary file in the same directory, fsync, rename, then fsync of the directory). An operation that writes several tables is not atomic as a whole: a merge writes up to nine tables one after another, and a roster apply or a resolve run several. A crash between two writes leaves the earlier tables written and the later ones not. Recovery is the restore below, from the backups that run took before its first write of each table. | A staging directory renamed at the end would make the set atomic; it has not been built. Until then the guarantee is per table, and the backups are what make a partial write recoverable. |
| A wrong merge is undone by hand, table by table, from these backups. There is no `unmerge` command. (A roster membership wrongly attached to a record is separated with `giye split`, see Splits under Identity: it gives that line a new record and a new `gy_id`; it does not reverse a merge of two records.) Restore every ledger table the merge wrote (`artists`, `gy_retired`, `frame_membership`, `activities`, `cv_sources`, `links`, `collaborations`, `review_queue`, `scope`) from its `<file>-<date>-before-merge*.csv.gz` copy, together with any later `before-apply-cv` copies the merge's CV fold wrote, then run `giye resolve` and `giye publish` again. Every later write to those tables (a later collect, extract, resolve or decision) is lost by the restore and has to be run again. The restore works only while those copies exist, that is within `[ledger] keep_backups_days` (or from the private repository or the VPS copy). Extraction files under `work/cv_extract/` are not renamed by a merge and need no restore, except when the merge collapsed two registrations of one CV URL: the files that named the dropped registration's `source_id` were rewritten to the kept one, and they must be put back by hand or re-extracted. | The backups are the bytes before the merge, so a restore is exact for the ledger. CV ownership is read from `cv_sources`, so once that table is restored each CV belongs to its own person again. |
| `[ledger] keep_backups_days` prunes backups dated more than that many days ago (date in the file name). Only package-named backups are deleted, and every backup on the newest day of each file is kept. Unset keeps everything. | Bounded disk use without ever leaving a ledger file with no backup. The private repository and the VPS copy (`deploy/backup.sh`) keep the longer history. |

## Derived values (stage 5)

Nothing in this stage edits the ledger. Checks become flags. Derivations become rows in `artist_attributes.csv`, each with the rule and the evidence. `processed/activities.csv` names its rules in two columns: `venue_rule` (the rules that put the row at its `venue_id`: V4, V7 when V7a–d rewrote the row's spelling, and each merge rule on the path from the row's key to the key of the entity's name, for example `V4|V7|V9`) and `rules` (every rule that filled a value of the row: P2, V1 when a place was resolved, P3, P4 when an edition link was made, and the Y-id of each P1 flag; the `flags` column keeps the long names). `venues.csv` has a `rules` column (the union over the entity's spellings), and `venue_merges.csv` lists every join (rule, entity, the two keys it joined) in a form a program can read; the audit's section 7 lists the same joins in Markdown. A value the artist row already holds wins (P5): `country` and `region` are derived only when both are empty, `active_since` only when that cell is empty, medium tags only when both `field` and `category` are empty. Birth year has no ledger column; it is only a derived row. Record depth (P6) also has no ledger column. It is one level per published person and is not copied into the site snapshot.

Place names, generic institution words, and romanisation come from a language module (`giye.normalize.language`). The Korean–English module is the default. Its glossary and compact gazetteer are files; the gazetteer includes every Korean first- and second-level administrative unit (17 regions; each city, county and district), derived from GeoNames KR.txt (CC BY 4.0). A full GeoNames tree is optional (`[normalize] reference`) and is not shipped.

A branch is a separate institution and is not joined. A Hangul branch is the entity plus a place and 관 (서울관, 과천관, 덕수궁관, 청주관). A Latin branch is the entity plus a city (MMCA Seoul, MMCA Cheongju). An acronym plus a place is joined to the acronym when the acronym is specific, the rows that write the bare acronym beside a city name that city most often (so the acronym is that site, not a word such as City or Loop that happens to precede a place), and no other spelling of that acronym names a different city or branch. A second site is any spelling that is the acronym plus a different gazetteer place (MMCA Cheongju, MMCA 과천, MCA Sydney and MCA Chicago), or a Hangul place-plus-관 branch of the same institution (국립현대미술관 청주관). A row that names no city is not evidence of a site. When the spellings name only one city, that city is the only site and the join stands (ZKM Karlsruhe, CERN Geneva). "Most often" means a unique maximum: when two cities tie, the acronym has no city of its own and is not joined. Why: until 2026-10-06 the tie went to whichever city came first in the ledger, so re-sorting the ledger changed the entities. | ported |
| V8b | An administrative office is not the place it administers. A district, city, county, or province plus 구청, 시청, 군청, 도청, or 주민센터, or plus City Hall or District Office, is not joined to the bare place by V8 or by any other merge rule (V5, V7e, V9). The office stays an institution. 노원구청 is not 노원구. | ported |
| V9 | A Hangul name and a Latin name are one entity when the Hangul name, read with the glossary, the gazetteer, and syllable romanisation for the rest, gives the same bag as the Latin name, the bag holds a proper word, and every link in the connected component uses that one reading. Two different readings in one component are ambiguous and are not merged. The first reading that matches anything is the one used (현대 = contemporary before modern). A reading that two Hangul institutions of the data share with different proper words is ambiguous and joins neither (V9 guard, like V5e): 시립 reads as nothing, so 예시미술관 and 예시시립미술관 give one bag, and neither is joined to Yesi Museum of Art. The proper words are compared with every dropped word kept as itself (`=시립`); spellings of one name (spacing, a qualifier) and keys already in one entity are not a second institution. X2 applies the same guard over every venue of the ledger. Why: before 2026-10-06 a Latin name joined two different Hangul institutions (pre-release audit N-3). | ported |
| G1 | An ISO alpha-2 or alpha-3 code is a country when the fragment is that code (`KR`, `KOR`). | ported |
| G3 | An uppercase two- or three-letter token after a place inherits that place's country (and, for Korea, its region). `Los Angeles, CA` stays in the US. | ported |
| G6 | A two-letter US postal abbreviation that is not itself a country code (`NY`) is the US, when G3 had no previous place. | ported |

The words of V7b, V7c, V7d, V8 and V8b (qualifiers, edition markers, the script and its spacing, building and room words, office markers) are the language module's `venue_words`; the examples above are the Korean–English module's. The packaged city table is a small gazetteer (it includes Yongin, which V1's example uses), plus `kr_places.tsv`: every Korean region (ADM1) and city, county and district (ADM2) with its GeoNames name, ASCII name and Hangul names, written from GeoNames KR.txt (CC BY 4.0) by `tools/build_kr_places.py`, so V3c and the V8 branch guard hold without a GeoNames tree (Cheongju, 청주, 종로구 are places; MMCA Seoul stays apart from MMCA when MMCA Cheongju is written). It fills only names the city table does not resolve. It does not list neighbourhoods or foreign cities beyond the small table. V3b also reads two agreeing place names without a comma as one place (`Seoul Korea`, `Tokyo Japan`, `서울 종로구`): head and tail resolve in one country and, inside Korea, one region. A GeoNames tree, when configured, resolves the same kind of name from cities15000 and, when the file is present, from a country extract (`KR.txt` or `allCountries.txt`).

The synthetic demo's venue strings exercise V7a (an exhibition title in 《》), V7b (the qualifier 외 on 서울시립미술관), V8 (서울시립미술관 전시실, a hall of that museum), and V9 (that name with Seoul Museum of Art). The audit records the V8 and V9 joins. V7a–d do not, because they change the key before the join; the demo summary still counts those trimmed spellings under V7. See `examples/demo/EXPECTED.md`.

G2, G4, and G5 are not named in the production source. The audit header says G1–G6. The remaining lookup steps, in order, are a Korean first-level region in Hangul, a city (the more populous row wins), an admin1 name, then a country name. A Korean administrative suffix is stripped before the second try (서울시 → 서울). The packaged gazetteer is a compact table plus the Korean administrative units derived from GeoNames KR.txt. The full GeoNames city list is CC BY 4.0 and is not shipped; `[normalize] reference` loads it when it is present. A country extract beside `cities15000.txt` adds the administrative divisions and neighbourhoods that file omits.

## Publication (stage 7)

These are the production site builder's decisions. They do not have E/F/P/V ids of their own. F4 is the coverage ratio the snapshot prints.

| Decision | Rule |
|---|---|
| Who is a page | In scope, http(s) source, a collection date, on an admitted roster, status empty / `PUBLISHED` / `STAGED`. A roster row is the evidence of participation. The population is the declared programme list, so only an admitted roster membership admits a person; a verified CV link (`cv_link_ok=yes`) deepens a record and does not admit anyone. One function (`giye.normalize.rules.published_ids`) decides this for both the site and P6. |
| Type | `collective` when the T1 team test marks the row, otherwise `individual`. |
| Tombstone | A `gy_id` that is not on a page stays at that URL as `HIDDEN_BY_REQUEST` or `WITHDRAWN`, with no name and no records. |
| Hidden stops processing | A person with status `HIDDEN_BY_REQUEST` is left out of every derived output the package builds: `giye publish` (a nameless tombstone only), `giye normalize` (nothing of theirs in `data/processed/`: activities, attributes, venues, manifest counts), `giye explore` (rim order and ties) and `giye audit` samples (`giye.ledger.ledger.without_hidden`). What stays: their ledger rows, the ledger backups, the archived original bytes of cited pages, and the request itself, so the hide can be reversed and audited. Not covered: an analysis outside the package that reads `data/ledger/` directly (for example research scripts in the private repository) must apply the same filter itself, and a result computed before the hide is not recomputed by the package. Why: a hide request is a request to stop processing (PIPA Art. 37), not only to leave the website. |
| Hidden is never merged | No merge touches a record with status `HIDDEN_BY_REQUEST`, on either side. `giye resolve` skips the pair (E1–E4, X1); `giye merge`, `giye decide … merge` and `Ledger.merge` refuse it with "hidden by request"; the internal `Ledger._merge_rows` refuses it as well, and a merge never sets a hidden row's status to `PUBLISHED`. Why: a merge retires one id with a redirect and moves names, activities and CV rows to the survivor, so either direction would publish the hidden person's data or remove the tombstone. `giye unhide` first if the person asks for the merge. Hiding is per record: a later roster row that A1–A6 do not attach to the hidden record becomes a new record (an open question for the author). |
| Redirect | A retired `gy_id` points at the survivor's current `gy_id`. The ledger already collapsed the chain. |
| Activity on the page | `publishable=yes`, a title, a year in 19xx/20xx, an http(s) source. Other types become `other`. |
| Background | CV sections education, employment, teaching, and press, minus scholarship-like titles, a future `upcoming` year, and a row whose note holds `ungrounded=` or `suppressed=<reason>` (a curator's removal). Not counted as practice. Why note keys: apply sets `publishable=no` on every background row as a section marker. |
| F4 on the site | `coverage_pct = round(100 * included / max(declared, included), 1)`, where `declared` is `roster_size_declared` in `frames.yml`: a size the programme states itself (its own page, catalogue, or press release), cited by `roster_size_source` (an http(s) URL; the loader refuses a size without one). Null (shown as unknown) when no size is declared. Why: `roster_count` is written from the collected rows, so included / max(roster_count, included) is 100% by construction and measures nothing. Only an independently stated size makes coverage a measurement. The displayed `roster_count` stays the greater of that key and the membership count. Per edition: an edition listed in `roster_size_declared_by_edition` (size and http(s) source, both required) gets the same ratio over that edition's members. Why per edition: programmes state how many they selected each year, rarely for their whole history. Edition sizes are not summed into the frame size, because the frame counts a returning person once and the edition sizes count them in every edition. |
| Citation | APA, Chicago, and BibTeX in the production dialog's shape. Author, title, version, and origin come from `[publish]`. Default author `기예 Giye` and default version `0.2`. There is no default origin: `[publish] site_url` is required. The version label carries the release date of the cited content (docs/SNAPSHOT.md). |
| Same-name note | Open `possible_same_person` items are listed on both pages as other ids. They are not merges. |
| Gap | A missing number up to the highest issued id is a warning. The snapshot is still written. |
| Roster must publish | A member who is not published and not out of scope stops the build. |

`giye publish` does not rewrite `frames.yml`. Production saved the new counts back into that file. The counts are in `frames.json` and `coverage.json`.

Region tags, the medium guess from `field` / `category`, and edition aliases are declared in the field file (`src/giye/fields/<name>/field.toml` for a field shipped as package data, or the path in `[paths] field`). An alias maps a membership code to a frame and an edition when that frame is registered. Another field supplies its own lists. They are data files, not rules compiled into the code.
